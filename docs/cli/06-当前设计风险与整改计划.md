# 当前设计风险与整改计划

> 建立日期：2026-08-03。本文是 Agent CLI P0 的工程风险台账。风险只有在代码、测试和文档三者一致后才能标记为“已修复”；概念设计或接口占位不等于能力可用。

## 1. 风险处理原则

整改优先保证事实可靠，其次才增加图的表达能力：

1. 状态只能由运行时修改；
2. 完成结论必须引用系统可验证的证据；
3. 所有文件变更都必须进入交付清单；
4. 循环停止原因、预算和审批必须可以持久化；
5. 沙箱和多层规划在没有执行器验证前不得写成已实现能力。

## 3. P0 验收证据

以下场景必须有自动化测试：

- 修改公开返回的节点快照不会改变图内部状态；
- 已就绪或已运行节点不能再增加入边；
- 硬条件 `PASS` 无有效证据时不能完成；
- N/A 软偏好不影响质量分；
- 新建文本文件、二进制文件和空文件都出现在变更清单中；
- 普通 ReAct 动作不消耗或触发重规划审批；
- Loop 明确返回完成、等待审批和预算耗尽；
- 事件重放后节点状态、attempt、output 和边与原图一致；
- 没有实际执行后端时，沙箱执行前检查必须拒绝放行；
- Git 超时和仓库内 worktree 根目录以受控错误结束。

## 4. 暂不宣称已解决的边界

本轮基础库整改不会自动获得以下能力：

- 操作系统级文件挂载、网络、环境变量、进程组和资源隔离；
- SQLite 事务、进程崩溃恢复与跨进程并发控制；
- `all_success`、`all_terminal`、quorum 等完整 Join Executor；
- TaskGraph、PhaseGraph、UnitLoop 的预算继承和局部重跑；
- 将 task worktree 变更自动应用到用户原工作区。

这些能力必须在受控执行器和一条真实的“规划 -> 修改 -> 验证 -> 评估 -> 审批 -> 交付”链路中单独评测。
