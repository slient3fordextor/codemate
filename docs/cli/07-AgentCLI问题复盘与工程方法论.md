# Agent CLI 问题复盘与工程方法论

> 建立日期：2026-08-03，最近更新：2026-08-04。本文记录 CodeMate 从对话后端、执行图基础库发展到受控 Agent CLI 纵向闭环期间出现的问题，以及可以复用于后续工具建设的方法。风险是否关闭仍以 [当前设计风险与整改计划](06-当前设计风险与整改计划.md) 为准。

## 1. 文档职责

本文不重复产品需求，也不把尚未实现的设计写成能力承诺。每个问题按五个要素记录：

1. 问题表现：用户或运行时实际能观察到什么；
2. 根因：哪个职责边界、状态事实或工程约束缺失；
3. 处理方式：当前采取了什么修复；
4. 验证证据：怎样证明修复真实生效；
5. 方法论：以后遇到同类问题应遵守什么原则。

状态使用“已修复”“部分修复”“未解决”三类。“有接口”“有配置”“有设计文档”不等于已修复。

## 2. 问题档案

### 2.1 产品文案领先于运行能力

- 问题表现：Web 曾展示 `agent/auto` 等模式，但后端只有普通聊天；Graph、Loop 和沙箱设计容易被误读为已经可以修改项目。
- 根因：产品目标、基础库能力和端到端能力没有分别标记，展示层可以声明运行时无法兑现的模式。
- 处理方式：Web 暂时只保留“对话”；CLI 按真实策略开放 `readonly`、`confirm`、`agent`。可写模式固定创建独立 worktree，修改经过 diff 提案，命令仅由 Bubblewrap 白名单执行，交付必须显式调用 `deliver`。
- 验证证据：CLI 冒烟覆盖 worktree 创建、Runner、SQLite checkpoint 和显式清理；自动化测试覆盖审批写入、沙箱、验证门槛和交付冲突。
- 方法论：能力必须以“入口可用、运行链路完整、失败可解释、自动化测试存在”四项同时成立为准。展示层只能枚举运行时注册的能力。

状态：已修复。

### 2.2 Graph 状态可以被外部引用破坏

- 问题表现：调用方可能修改公开返回的节点对象，或者在目标节点激活后追加依赖，导致就绪状态与事件记录不一致。
- 根因：执行事实层暴露了可变内部对象，拓扑冻结规则不完整。
- 处理方式：对外返回隔离快照；节点离开 `pending` 后冻结入边；拒绝重复边；所有状态变化经运行时并记录事件。
- 验证证据：测试修改节点快照后内部状态不变，并覆盖激活后加边、重复边和事件重放。
- 方法论：状态机的对象所有权必须属于运行时。调用方只能提交命令或读取快照，不能直接持有可变事实。

状态：已修复；图事件由带 schema 版本的 SQLite 追加事务持久化并通过事件重放恢复。

### 2.3 Loop 停止原因和预算语义含混

- 问题表现：早期 Loop 用空值混合表达完成、预算耗尽和等待审批；普通 ReAct 工具动作也可能误耗重规划预算。
- 根因：控制流结果没有类型化，迭代、重规划和审批使用了相互混淆的计数器。
- 处理方式：`GraphLoop` 返回 `continue`、`complete`、`wait_for_approval`、`budget_exhausted`；ReAct 默认 10 轮，第 11-15 轮要求新证据，超过 15 轮逐轮批准；重规划单独计数。
- 验证证据：测试覆盖停止类型、重复消费验证、重规划审批绑定和预算耗尽；CLI 非交互模式在需要审批时停止。
- 方法论：任何自循环都必须同时拥有明确终态、迭代上限、Token 上限、失败上限、时长上限和人工升级入口。审批必须绑定具体动作或轮次，不能成为永久放行。

状态：已修复；Loop checkpoint 与图事件分别持久化。

### 2.4 “模型认为完成”被当成确定性结论

- 问题表现：没有测试或 Artifact 时，模型自报 `PASS` 也可能形成完成结论；软质量分可能掩盖安全或交付失败。
- 根因：评估声明与受信任证据没有分离，硬门槛与软偏好共用模糊分数。
- 处理方式：`EvaluationContract` 要求 `PASS` 引用类型匹配的有效证据；Bubblewrap 命令生成受信任 Artifact；可写 Runner 要求最新编辑之后存在成功命令证据，否则返回 `needs_evidence`。
- 验证证据：测试覆盖无证据 PASS、错误证据类型、失效证据、N/A 分母和最低质量阈值。
- 方法论：模型只能提出结论，Executor 才能生成事实。完成判断应先过硬门槛，再讨论软质量；质量分不能覆盖权限、安全和必要验证失败。

状态：已修复。

### 2.5 只读工具仍可能泄露敏感信息或间接执行程序

- 问题表现：路径限制如果只检查字符串，符号链接可以逃出工作区；`.env.local`、私钥和凭据文件可能进入模型上下文；`git status/diff` 可能受 fsmonitor、hook、external diff 或 textconv 配置影响。
- 根因：“只读”被简单理解为不调用写 API，没有覆盖路径规范化、内容分类、输出预算和工具的隐式扩展点。
- 处理方式：解析真实路径后校验工作区边界；拦截敏感文件名、后缀和私钥内容；限制文件、树和输出大小；Git 固定 argv、超时，并关闭 fsmonitor、hook、external diff、textconv、全局和系统配置。
- 验证证据：测试覆盖路径穿越、符号链接、`.env` 变体、密钥文件、未知参数和输出缓存；真实仓库 Git 只读调用通过。
- 方法论：工具安全必须检查“显式动作、隐式扩展点、输入边界、输出边界、超时和环境继承”六个维度。只读不天然等于无副作用。

状态：已修复；编辑、命令和交付工具已按相同六维边界单独验收。

### 2.6 API 默认信任部署环境

- 问题表现：服务绑定 `0.0.0.0` 后，模型、记忆和配置接口可能被未授权访问；只校验客户端 IP 还存在 Host/DNS rebinding 风险。
- 根因：本地优先被当作部署假设，而不是运行时强制策略；限流配置没有接入中间件。
- 处理方式：默认只允许 loopback 客户端和可信本地 Host；远程访问必须显式启用并配置 Bearer Token；API 增加进程内固定窗口限流。
- 验证证据：测试覆盖默认拒绝远程、非可信 Host、错误 Token、正确 Token和限流配置。
- 方法论：安全默认值必须由代码强制，不能依赖 README。认证、来源限制和限流是不同边界，不能相互替代。

状态：已修复；本地多进程可配置共享 SQLite 限流，多机部署继续由网关承担统一边界。

### 2.7 配置写入位置、优先级和并发不一致

- 问题表现：页面保存模型配置后可能写到与运行时读取位置不同的 `.env`；并发请求可能互相覆盖；进程环境变量会让文件更新看似成功但实际不生效。
- 根因：配置来源优先级没有进入更新协议，文件更新不是原子事务。
- 处理方式：写入运行进程实际加载的根目录 `.env`；环境变量托管的字段返回冲突；使用进程锁、临时文件、`fsync`、原子替换和 0600 权限。
- 验证证据：测试覆盖工作区与运行目录不同、环境变量覆盖和最终文件权限。
- 方法论：配置管理必须同时定义“读取来源、优先级、可写来源、并发协议和生效时机”。更新接口不能承诺自己无法改变的高优先级配置。

状态：已修复；文件更新同时使用线程锁、跨进程文件锁、原子替换和缓存失效。

### 2.8 流式模型请求的重试边界不清楚

- 问题表现：存在 `max_retries` 配置但适配器不重试；如果在输出开始后盲目重试，又会把部分回答重复发送给用户。
- 根因：普通 HTTP 重试策略直接套用到流式协议，没有定义“提交点”。
- 处理方式：只在首个流式输出前重试超时、传输错误、429 和 5xx，并使用有限退避；一旦开始输出，失败直接上报。
- 验证证据：适配器测试覆盖首块前失败后成功，以及不可重试错误。
- 方法论：流式操作必须明确不可逆提交点。提交点之前可以按幂等策略重试，之后必须避免重复输出或重复副作用。

状态：已修复；模型只在提交点前重试，命令不自动重试，未知中断结果恢复后必须重新审批。

### 2.9 健康与日志报告的是“请求开始”而非真实结果

- 问题表现：记忆存储不可用时健康接口仍可能返回正常；SSE 访问日志在流消费前记录，延迟数据不代表用户实际等待时间。
- 根因：可观测性只检查对象是否创建和响应头是否生成，没有覆盖关键依赖和流式生命周期。
- 处理方式：记忆存储协议增加 `ping`；依赖降级时健康接口返回 503；StreamingResponse 在迭代结束后记录完整延迟。
- 验证证据：健康接口和存储实现测试、完整 API 测试通过。
- 方法论：健康检查要验证完成关键路径所需的依赖；流式请求的成功、错误和耗时必须以流结束为边界。

状态：已修复；`/api/v1/health?probe_model=true` 提供显式、可能产生模型调用的深度探活。

### 2.10 构建结果缺少持续门禁和依赖边界

- 问题表现：依赖仅设置下限，上游主版本升级可能破坏项目；没有仓库级 CI 强制运行 lint、类型检查和测试。
- 根因：本地验证依赖开发者习惯，没有形成可重复的交付约束。
- 处理方式：依赖增加主版本上限；GitHub Actions 统一执行 `ruff`、`mypy app` 和 `pytest`；Makefile 增加一致的 `check` 入口。
- 验证证据：本轮完整检查为 102 个测试通过，lint 和类型检查通过。
- 方法论：修复只有进入持续门禁才算稳定。版本范围负责兼容边界，锁文件负责精确复现，两者不能互相替代。

状态：已修复；`requirements.lock` 作为 pip constraints 锁定 CI 解析结果。

### 2.11 严格 JSON 决策协议仍会浪费模型轮次

- 问题表现：不同模型可能输出 Markdown、解释文本或错误字段，Runner 需要再次提示修复，增加延迟和 Token。
- 根因：当前只读纵向切片用提示词模拟工具协议，尚未统一 OpenAI 与 Anthropic 的原生 tool-call 事件。
- 处理方式：统一模型层 `tool.call.*` 事件，OpenAI-compatible 与 Anthropic 分别映射原生工具协议；不支持原生协议的适配器继续使用严格 JSON 兼容层。
- 验证证据：测试覆盖原生分块参数汇聚、非法 JSON 修复、未知工具参数拒绝和只读结果缓存。
- 方法论：提示词约束只能作为兼容层，不能作为最终执行权限。任何模型输出在进入 Graph 和 Executor 前都要经过结构化验证。

状态：已修复。

### 2.12 写入、命令、worktree 和恢复曾缺少统一事务边界

- 问题表现：现有基础库分别讨论补丁、沙箱和 worktree，但尚不能安全完成“修改 -> 验证 -> 中断恢复 -> 交付”；进程退出后 Runner 图会丢失。
- 根因：副作用能力不是单个工具问题，而是 Policy、Approval、Executor、Artifact、事件事务和交付协议的组合问题。
- 处理方式：任务使用独立 worktree；SQLite 保存任务、图和 Loop 状态；文件先提案再按审批 ID 原子写入；验证命令在无网络 Bubblewrap 中运行；交付前检查基线重叠并执行 `git apply --check`。
- 验证证据：自动化测试覆盖未经审批不写入、摘要并发保护、沙箱断网、文本/二进制/空文件清单、成功交付与重叠冲突；真实 CLI 冒烟覆盖创建、checkpoint、恢复状态和清理。
- 方法论：副作用能力必须按纵向闭环交付，不能分别实现几个类后就开放入口。隔离负责影响范围，审批负责授权，事件日志负责恢复，三者不能互相替代。

状态：已修复；Linux 缺少 Bubblewrap 时仍按设计 fail-closed。

## 3. 形成的工程方法

### 3.1 能力完成判定

一项 Agent 能力只有同时满足以下条件才可标记为已实现：

```text
产品入口
  + 真实运行链路
  + 安全与权限边界
  + 失败/取消/恢复语义
  + 自动化验证
  + 与代码一致的文档
  = 可对外声明的能力
```

缺少任一项时，应标为“基础库”“部分修复”或“设计方案”。

### 3.2 实施顺序

后续能力默认按以下顺序推进：

1. 先定义事实、状态和失败语义；
2. 再定义策略、预算和不可绕过的边界；
3. 实现一条最小纵向链路；
4. 为安全边界和失败路径添加测试；
5. 接入 CLI 展示与审批；
6. 进行中断、重复执行和恶意输入验证；
7. 最后才扩大工具范围和并行度。

### 3.3 三层判断

每次设计评审分别回答三个问题：

| 层次 | 核心问题 | 失败时的处理 |
| --- | --- | --- |
| 事实层 | 系统实际发生了什么，有什么可信证据 | 返回 `unknown/needs_evidence`，不能猜测完成 |
| 控制层 | 当前动作是否满足依赖、权限、预算和恢复规则 | 等待、拒绝、取消或进入受控重试 |
| 质量层 | 在硬条件满足后，是否值得继续优化 | 在剩余预算内排序处理，耗尽后交付当前结果 |

### 3.4 性能优化顺序

CodeMate 的默认取舍不是单独追求最低延迟或最少 Token，而是在事实可靠和安全边界成立后优化有效完成成本：

1. 删除重复工具调用和无效模型轮次；
2. 只传递相关 Artifact 或有预算的摘要；
3. 并行独立且无共享副作用的读取或验证；
4. 缓存确定性只读结果，并标记证据是否仍然新鲜；
5. 只有基准数据证明收益后才增加多层规划和复杂 Join。

## 4. 后续复盘模板

新增问题时，在本文追加问题档案，并至少填写：

```text
问题标题：
发现日期：
关联风险 ID：
问题表现：
影响范围：
根因：
修复或隔离方式：
验证证据：
是否存在兼容性影响：
可复用方法：
当前状态：已修复 / 部分修复 / 未解决
```

风险状态发生变化时，先更新风险台账，再更新本文对应条目的状态和验证证据，避免方法论总结与当前实现脱节。
