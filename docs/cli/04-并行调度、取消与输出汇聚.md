# 并行调度、取消与输出汇聚

> 状态：P0 设计约束，尚未接入执行器。本文基于 2026-08-03 的公开资料调研，用于指导自研轻量执行图实现。

## 1. 结论

并行读取和并行验证可以显著缩短用户等待时间，但它们不能只由“图上分出了两个分支”决定。CodeMate 必须同时定义：资源锁、并发配额、取消传播和输出汇聚策略。

推荐原则：**并行是安全独立工作的优化；副作用和事实汇聚必须可解释。**

对于可写任务，优先以 [Git worktree 隔离](05-Git工作树隔离策略.md) 消除跨任务目录冲突，再将 task worktree 作为 Sandbox 的唯一可写 `/workspace`，并在其中应用资源锁与并发配额。

```text
Graph Scheduler
  -> 检查依赖与 Join 条件
  -> 获取 ResourceLock 和并发配额
  -> 在一个结构化并行组中启动 Executor
  -> 取消/失败向组内任务传播
  -> 各分支保存 Artifact
  -> Join 按策略汇聚结构化结果
```

## 2. 市面样例

| 主题 | 参考实现 | 可借鉴之处 | 不直接满足之处 |
| --- | --- | --- | --- |
| 并行 fan-out/fan-in | LangGraph | 同一 super-step 并发，后续节点等待分支完成 | 不理解本地文件路径或工作区命令的资源冲突 |
| 状态汇聚 | LangGraph reducer | 并行更新同一字段必须定义合并函数；分支顺序不保证稳定 | 原始输出直接进入共享状态会浪费 Token |
| 并发上限 | LangGraph `max_concurrency`、Prefect concurrency limits | 为任务或类别设置全局并发配额 | 不等于同一文件写入的排他锁 |
| fail-fast 取消 | Python `asyncio.TaskGroup` | 一个子任务发生真实异常时，取消同组未完成任务并等待退出 | 只能协作式取消；阻塞 I/O 与子进程需要执行器配合 |
| 长任务取消 | Temporal cancellation | 取消向子工作流/活动传播，适合耐久任务 | P0 不需要引入完整 Temporal 运行时 |

资料：[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api)、[LangGraph 并发状态更新](https://docs.langchain.com/oss/python/langgraph/errors/INVALID_CONCURRENT_GRAPH_UPDATE)、[Python asyncio TaskGroup](https://docs.python.org/3/library/asyncio-task.html#task-groups)、[Temporal Python Cancellation](https://docs.temporal.io/develop/python/workflows/cancellation)。

## 3. 资源锁与并发配额

### 3.1 两类限制不可混淆

- **资源锁**解决正确性：两个操作是否可同时接触同一资源。
- **并发配额**解决性能与容量：同类操作在一个时刻最多执行多少个。

仅设置 `max_concurrency` 无法阻止两个补丁同时修改同一个文件；仅设置文件锁也无法防止同时启动大量模型请求或测试进程。

### 3.2 P0 资源键

| 资源键 | 锁模式 | 使用节点 |
| --- | --- | --- |
| `read:{normalized_path}` | 共享锁 | `read`、只读解析 |
| `write:{normalized_path}` | 排他锁，并与同路径读取互斥 | `apply_patch`、创建/删除文件 |
| `workspace:command` | 默认排他锁 | `command`、构建、测试、格式化 |
| `workspace:git-index` | 排他锁 | 后续 Git 暂存、提交类操作 |
| `model:{provider}` | 无锁，使用信号量 | `model` |
| `network:{host}` | 无锁，使用信号量 | 后续远程 MCP、网络工具 |

路径必须先由文件安全层归一化并确认处于工作区内，资源键不能直接使用模型提供的原始文本。

### 3.3 默认配额

初始值只作为可观测的保守默认，不是性能承诺：

| 类别 | 默认上限 | 原因 |
| --- | --- | --- |
| 文件读取/搜索 | 4 | 对独立上下文收集有明显延迟收益，避免大量小文件冲击上下文 |
| 模型请求 | 2 | 控制 API 限流、Token 成本和输出汇聚复杂度 |
| 工作区命令 | 1 | 测试、构建、格式化可能争用缓存、临时文件和构建产物 |
| 单文件写入 | 1/路径 | 保证 diff、撤销与恢复语义明确 |
| 网络工具 | 2/host | 为未来外部服务保留速率控制边界 |

最终参数依据真实项目的任务完成率、首个可见反馈、总耗时、Token 和资源占用评测后调整。

## 4. 取消规则

### 4.1 取消来源

- 用户取消当前 `TaskRun`；
- 高优先级安全策略或 guardrail 触发；
- 并行组中的 fail-fast 节点产生不可恢复错误；
- 节点超时或整个任务超时；
- 进程退出或崩溃恢复时发现不应自动重试的运行中节点。

`waiting` 是暂停等待用户，不是取消；拒绝审批是取消该节点或进入其拒绝分支，不应静默取消整个图。

### 4.2 传播模型

```text
TaskRun cancel
  -> Scheduler 停止启动新的 ready 节点
  -> Scheduler 对当前 parallel group 的 Task 逐个调用 cancel()
     （或以受控异常退出 TaskGroup，使其取消剩余兄弟任务）
  -> Executor 收到 CancellationToken
  -> HTTP/模型流关闭；子进程终止其进程组；文件写入完成原子回滚或记录结果
  -> 节点写入 cancelled / interrupted 事件
  -> Join 依据已保存 Artifact 进入 cancelled 或 all_terminal 汇聚
```

Python `asyncio` 的取消是协作式的：`CancelledError` 会在下一个等待点注入协程。Executor 必须用 `try/finally` 清理资源并继续传播取消；不得吞掉异常后伪装为成功。

### 4.3 fail-fast 与收集全部结果

| 并行组类型 | 默认策略 | 示例 |
| --- | --- | --- |
| 安全门禁 | fail-fast | 敏感内容检测、策略检查失败后停止后续高风险分支 |
| 读取与检索 | 收集全部结果 | 一个文件读失败仍保留其他文件和错误证据 |
| 验证 | 收集全部结果 | 测试失败时仍收集类型检查、格式化结果 |
| 相互替代的信息源 | 首个可信结果后可取消其余分支 | 后期多个等价只读检索工具 |
| 写入与命令 | 默认串行 | 避免共享工作区副作用与不确定回滚 |

## 5. 输出汇聚

### 5.1 分支输出必须先变成 Artifact

分支不直接把完整 stdout、源文件或模型文本广播给所有后续节点。每个分支保存一个结构化 Artifact：

```text
branch_id
source_node_id
type
status
summary
raw_reference
token_count
completed_at
```

- `summary` 用于默认下游上下文，受 Token 预算限制；
- `raw_reference` 指向可按需读取的完整输出或文件快照；
- `status` 必须表达成功、失败、取消、跳过或部分完成；
- 输出序列按稳定的 `branch_id` 或节点创建顺序排序，不能依赖并发完成顺序。

### 5.2 Join 策略

| Join | 适用场景 | 成功条件 | 输出 |
| --- | --- | --- |
| `all_success` | 补丁依赖、关键前置条件 | 所有必需分支成功 | 所有成功 Artifact |
| `all_terminal` | 读取、搜索、验证 | 全部分支达到终态 | 成功/失败 Artifact 与完整状态摘要 |
| `any_success` | 相互替代的只读来源 | 至少一个可信分支成功 | 首个成功 Artifact，记录被取消分支 |
| `quorum` | 后期多 Agent 审查 | 达到定义的可信票数 | 证据、分歧和裁决依据 |

P0 实现 `all_success` 与 `all_terminal`；`any_success`、`quorum` 留待工具可信度和多 Agent 策略明确后实现。

### 5.3 验证结果的交付规则

验证 Join 只陈述证据，不直接替用户宣称任务成功：

- 所有验证通过：可标记“验证通过”。
- 任意验证失败：最终总结必须列出失败命令、退出码和摘要。
- 验证未执行或被取消：必须显式写出原因。
- 仅部分验证完成：可交付修改摘要，但任务状态不能标记为“完全验证成功”。

## 6. P0 实现顺序

1. 引入资源键、共享/排他锁及各类别信号量，先覆盖内存图调度。
2. 使用 `asyncio.TaskGroup` 执行独立只读节点，实现 fail-fast 和收集全部两种策略。
3. 将取消令牌传递给未来模型、文件和命令 Executor，并记录取消/中断事件。
4. 实现 `Artifact` 与稳定排序的 `all_success` / `all_terminal` Join。
5. 用读取、验证、取消、同路径写入冲突和部分失败场景做评测。

在完成第 1 至第 4 步前，不启用并行命令、并行写入或将原始分支输出直接拼接进模型上下文。
