# Agent 执行图设计与评测

## 状态

**基础内核已实现，整体方案仍待评测。**

当前已实现 `app/agent/graph/` 中的内存执行图状态机、隔离节点快照、激活后入边冻结、依赖/条件就绪计算、审批等待/恢复、运行中断标记、内存事件重放，以及将有限循环展开为追加式节点的 `GraphLoop`。SQLite 事件存储、并发执行器、策略引擎、工具、真实沙箱和 CLI 渲染仍未接入，因此当前内核不能执行模型、文件或命令操作。

本文将执行图（Execution Graph）作为 CodeMate Agent CLI 的候选运行内核。它解决多个执行单元的连接、条件分支、并行、人工等待、失败处理和进程中断后的恢复问题。

该方案不替代模型。模型负责理解用户目标、依据工具结果提出下一步；执行图负责约束和记录步骤实际能否执行、何时执行、执行失败后去向何处。

## 使用哲学

执行图是 CodeMate 的**执行事实层**，不是提示词、思维链、聊天记录，也不是为了形式化而把每个模型动作画成节点。它只表达用户和系统需要看见、控制、恢复或审计的执行事实。

### 图管执行，模型管决策

- 模型负责理解目标、解释证据、提出受 schema 约束的下一步建议，以及在信息不足时提出问题。
- 图负责依赖、条件、并行、权限、等待、取消、重试、恢复和终态；模型不能跳过图直接操作文件、执行命令或提升权限。
- 工具结果、当前文件和验证输出是事实来源，优先级高于模型推测和历史记忆；图只把已记录的事实传递给下游。

### 节点必须是有边界的工作

一个节点应对应一次可命名、可限额、可观察的工作，例如读取一组文件、提出补丁、应用已确认 diff、运行测试或汇聚验证结果。模型的 token 流、内部推理和纯展示文本不是节点。

每个节点必须声明输入、输出 schema、允许工具、权限类别、超时、Token/输出预算、重试与恢复策略。写文件、命令、联网等副作用节点还必须声明幂等键或明确标为不可自动重试。

### 图保持稀疏，循环受控展开

运行中的图实例保持**追加式、可追溯、无任意回边**。当某个执行单元需要迭代时，不让模型或节点在内部无限 `while` 循环，而是由 `LoopController` 根据可验证的退出条件创建下一次迭代节点和边：

```text
诊断(第 1 次) -> 修复(第 1 次) -> 验证(第 1 次)
                                      -> 未通过且预算允许
                                      -> 诊断(第 2 次) -> ...
```

这样每次尝试都有独立的输入、证据、Token 和副作用记录；恢复、取消、比较和人工介入都不会依赖隐藏的栈帧。循环必须同时受最大次数、总 Token、总时长、失败次数和明确成功/升级条件限制。

`GraphLoop` 不用 `None` 混合表达停止原因，而是返回 `continue`、`complete`、`wait_for_approval` 或 `budget_exhausted`。返回值携带迭代数、Token、重规划数、待审批来源和已消费验证 ID；同一验证结果不能被重复消费。达到重规划上限后，恢复必须走独立审批入口，避免把同一次验证的 Token 重复计入。

### 并行是优化，不是默认行为

只有输入独立、没有共享副作用、结果无需彼此作为前提的节点才可并行。文件读取、搜索和独立静态检查通常可并行；同一路径写入、依赖构建产物的命令、需要同一交互输入的节点必须串行或加资源锁。

并行分支传递 artifact 引用或受预算约束的结构化摘要，不能把全部原始输出广播到每个分支或后续模型调用。

### 等待与恢复优先于“自动继续”

未知权限、歧义目标、危险副作用和不可安全重试的中断，都应将节点置为 `waiting`，由用户决定后续动作。恢复的默认目标是“不重复产生副作用且能说明已发生什么”，不是不经检查地继续自动执行。

### 严谨来自证据与验证

完成不等于模型说“已完成”。对代码任务，完成条件至少应包括：变更 diff 已记录、相关验证已执行或明确说明未执行、失败与不确定性未被隐藏。图的最终总结节点只能引用已保存的工具事实、验证结果和用户批准记录。

### ReAct 的性能预算

P0 采用自研轻量状态机，ReAct 只是 Agent 单元内受控的探索策略。单元默认最多自动执行 10 轮；第 11 至第 15 轮只有在本轮产生新的工具证据或验证进展时才能继续。已完成 15 轮后，运行时将节点置为 `waiting`，必须获得用户确认才创建下一轮；批准绑定明确的下一轮编号，只覆盖这一次继续执行，后续超限轮次仍需再次确认。

每轮同时受到工具白名单、单元 Token 预算、总时长、失败次数和重规划次数限制。P0 默认最多重规划 3 次；只有本轮动作明确为 `replan` 时才检查和消耗该预算，普通工具动作不受重规划上限误伤。达到上限后进入 `waiting`，批准绑定下一次重规划编号。ReAct 不用于已批准的补丁应用、文件读取和已批准命令等确定性动作。

### 多维确定性评估与软质量偏好

最终回答由 `EvaluationContract` 评估，而不是由模型自评。每个条件独立记录 `pass`、`fail`、`unknown` 或 `not_applicable`，声明允许的证据类型，并关联 Artifact/批准/命令等证据 ID。`pass` 只有引用证据目录中有效且类型匹配的证据才成立；例如审批记录不能证明测试通过。证据生成仍必须由后续受信任的工具 Executor 负责，模型不能自行登记有效证据。

- 硬门槛：安全、权限、必要交付物、显式要求的验证和基线一致性；任一 `fail` 为 `blocked`，任一 `unknown` 为 `needs_evidence`。
- 软质量偏好：测试覆盖、代码风格、性能、额外验证与风险披露；以权重形成质量分数和待改进项，但不会掩盖硬门槛结论。

`not_applicable` 的软偏好不进入质量分母。软偏好默认只用于排序和是否值得继续优化；只有产品显式配置 `minimum_quality_score` 时，低于阈值才返回 `needs_improvement`，且后续优化仍受 Loop 预算约束。

ReAct 与所有可追加下一轮的 `GraphLoop` 都必须先读取评估结果：优先补齐未满足硬门槛；只有硬门槛全部满足后，才可在剩余预算内处理软质量偏好。循环达到迭代、Token、重规划、时长或失败上限时，必须停止、交付当前评估或等待用户确认，不能静默继续。

## 1. 问题定义

普通的 Agent loop 通常是：模型决定工具调用，工具执行，结果回灌模型，直到模型结束。它适合单线任务，但难以可靠处理以下场景：

- 同时读取多个互不依赖的文件、运行多个独立检查；
- 等待用户确认 diff 或命令后再继续；
- 一个验证失败后返回诊断节点，而另一个验证已成功；
- CLI 进程退出或崩溃后恢复未完成任务；
- 记录每次写入、命令、审批与失败证据，避免把模型文本当作执行事实。

执行图要把“下一步做什么”与“这个步骤是否可以、何时可以被执行”分离。

```text
用户目标
  -> Planner 规划/追加节点
  -> Policy 检查权限
  -> Scheduler 调度可运行节点
  -> Executor 执行工具或模型节点
  -> Event Log 写入结果
  -> 下游节点被唤醒、跳过、失败或等待
```

## 2. 候选模型

### 2.1 图对象

| 对象 | 职责 | 核心字段 |
| --- | --- | --- |
| `TaskRun` | 一次用户任务的运行实例 | `id`、工作区、模式、状态、创建/结束时间 |
| `GraphNode` | 一个可恢复的执行单元 | `id`、类型、状态、输入、策略、重试配置 |
| `GraphEdge` | 节点之间的流转关系 | 上游/下游节点、触发条件、条件表达式 |
| `NodeAttempt` | 节点的一次执行尝试 | 次数、输入快照、结果、错误、开始/结束时间 |
| `Approval` | 人工等待和决定 | 请求摘要、批准范围、决定、过期时间 |
| `Artifact` | 大型或敏感结果的引用 | diff、命令输出、文件快照、脱敏状态 |
| `Event` | 不可变的运行事件 | 类型、对象 ID、时间、结构化载荷 |

节点类型首期限定为：`model`、`read`、`search`、`git`、`propose_patch`、`apply_patch`、`command`、`approval`、`join`、`summary`。不允许模型自定义任意可执行节点类型。

### 2.2 状态机

```text
pending -> ready -> running -> succeeded
                    |           |
                    v           v
                 waiting      skipped
                    |
                    v
                 ready / cancelled

running -> interrupted -> ready（安全恢复） / waiting（要求决定）
running -> failed -> ready（可重试） / cancelled / terminal
```

- `pending`：尚未满足依赖或条件。
- `ready`：依赖、条件和授权均已满足，可被调度。
- `running`：执行器已经接管该节点。
- `interrupted`：执行进程在节点完成前中断，尚未假定工具是否产生副作用。
- `waiting`：等待用户批准、外部输入或明确的恢复动作。
- `succeeded`、`skipped`、`failed`、`cancelled`：终态。

节点创建、边追加和任何状态转移都必须写入事件日志。当前内存事件包含 graph ID、attempt、output/error 和审批决定，可重放得到相同的拓扑与节点状态；SQLite 事务、事件 schema 版本与崩溃恢复仍属于阶段 C，不能只依赖当前内存重放。

### 2.3 边与汇聚

| 边类型 | 触发条件 | 示例 |
| --- | --- | --- |
| `success` | 上游成功 | 读取文件后进入分析 |
| `failure` | 上游失败 | 测试失败后进入诊断 |
| `always` | 上游任意终态 | 清理临时资源 |
| `condition` | 上游输出满足结构化条件 | 有 diff 时进入审批，否则直接总结 |

`join` 节点声明汇聚策略：`all_success`、`all_terminal`、`any_success`、`quorum`。首期只实现 `all_success` 与 `all_terminal`，避免过早引入复杂的部分成功语义。

## 3. 运行语义

### 3.1 示例：修复并验证

```text
理解任务
  -> [并行] 读取目标文件 / 查找相关测试 / 获取 Git 状态
  -> 汇聚上下文
  -> 模型分析并提出补丁
  -> 等待写入确认
  -> 应用补丁
  -> [并行] 运行相关测试 / 类型检查 / 格式化检查
  -> 汇聚验证结果
  -> 成功总结
     \-> 有验证失败：诊断 -> 修复建议或新的确认节点
```

并行只用于没有共享副作用的节点。文件写入按规范化目标路径互斥；同一工作区的命令是否并行，由命令风险和沙箱资源策略决定。

### 3.2 人工等待

写文件、运行命令、联网或其他策略要求确认的工具调用，不进入执行器，而是生成 `Approval` 并把节点置为 `waiting`。用户可以：

- 批准本次操作；
- 批准同类操作直到当前任务结束；
- 拒绝；
- 取消整个任务。

批准或拒绝本身是事件。恢复时，未过期且未决定的审批仍保持等待，不重新向模型询问。

### 3.3 失败、取消与重试

- 节点失败只影响依赖它的下游节点；图是否终止由失败边和任务策略决定。
- 只对显式声明为幂等的安全读取、搜索和部分模型调用自动重试。
- 文件写入、命令执行与网络操作默认不自动重试；必须由用户或新的图节点明确触发。
- 取消时停止未开始节点，并向可取消执行器发送取消请求；已完成的写入、diff 和工具结果不被抹除。

### 3.4 恢复

任务恢复以持久化状态和事件为准：

1. 读取尚未终态的 `TaskRun`。
2. 将进程中断时处于 `running` 的节点标记为 `interrupted` 事件。
3. 根据节点的恢复策略，将可安全重试的节点放回 `ready`，其余节点置为 `waiting` 并要求用户决定。
4. 从持久化的 `ready`、`waiting` 状态继续调度，不依赖模型记忆恢复流程位置。

首期的恢复重点是“不会重复产生副作用”和“用户能看到中断前发生了什么”，不是保证任何外部命令都可无缝继续。

## 4. 与现有 CodeMate 的关系

可复用能力：

- `app/adapters/models/` 的供应商模型适配与流式输出转换；
- `app/services/context_budget.py` 的整体上下文 Token 预算；
- `app/services/language/` 的语言识别和规则式项目提示；
- 会话记忆的存储协议和敏感内容处理经验。

需要新增的能力：

```text
app/agent/
  graph/        # 图定义、状态机、事件与调度
  planner/      # 模型规划与结构化节点提议
  policy/       # 授权模式、工具与风险判定
  tools/        # 文件、搜索、Git、补丁、命令的统一协议
  sandbox/      # 命令隔离后端
  storage/      # TaskRun、图和事件的持久化
  runner.py     # CLI/API 可复用的入口服务
app/cli/        # TTY 渲染、输入、确认和命令入口
```

`ChatService` 保持为纯对话流服务，或在未来作为只含 `model` 节点的兼容层。不能直接在它内部叠加文件写入、调度或审批逻辑，否则 Web 对话链路和 CLI Agent 链路会难以维护。

## 5. 待评测问题

本方案方向成立前，需要先验证以下问题，而不是立即投入完整实现。

| 主题 | 待验证问题 | 通过标准 |
| --- | --- | --- |
| 图是否必要 | 真实编码任务中是否存在足够的并行、等待、分支和恢复需求，值得高于简单 Agent loop 的复杂度 | 使用 10-20 个代表任务比较，图方案能更清晰处理至少 3 类非线性流程 |
| 动态程度 | 模型追加节点与预定义工作流分别能覆盖哪些任务 | 首期使用受限节点类型和动态追加，不能允许模型任意改写已执行图 |
| 持久化成本 | SQLite 事件记录、并发锁和恢复是否足够可靠 | 单机多次中断恢复不丢失已确认状态，也不重复文件写入 |
| 人机体验 | 多次确认会否使 CLI 过于打断工作 | 默认模式下每个副作用都有解释；同类授权能有效减少重复确认 |
| 并行收益 | 文件读取和验证并行是否实际缩短任务时间 | 有独立分支时首期原型相对串行基线存在可观察收益，且输出不混乱 |
| 可解释性 | 用户能否理解当前执行到哪里、为什么等待或失败 | 用户只看 CLI 事件即可说明任务状态、下一步和已发生副作用 |
| 安全 | 图调度是否引入工具绕过或恢复时重复副作用 | 权限始终在执行前判定；写入/命令恢复默认 fail-closed |

## 6. 评测计划

### 阶段 A：纯内存原型（已完成）

已实现最小图状态机、`success/failure` 边、带身份的 `approval` 等待/恢复、并行就绪计算、内存事件重放和受预算约束的类型化 `GraphLoop`。测试覆盖状态快照隔离、拓扑冻结、状态转移、并行依赖、循环展开、审批恢复、证据类型与回边拒绝；不接模型、不写入项目。

目标是先验证状态语义和 CLI 呈现，而不是优化存储或并发。

### 阶段 B：受控工具原型

接入只读文件、搜索和 Git 工具；增加独立读取节点的并行、`all_success` 汇聚和事件输出。使用固定任务图验证调度顺序、输出稳定性和 Token 上下文汇聚。

### 阶段 C：副作用与恢复原型

接入 diff 生成、确认后的补丁应用和受限命令执行。引入 SQLite 事件持久化，并刻意中断进程，验证恢复不会重复写入或重复启动命令。

### 阶段 D：模型规划接入

模型只能输出受 schema 校验的节点提议；策略层检查后才能追加到图。选择真实的修复、重构、测试失败排查任务，与串行 Agent loop 对比完成率、耗时、确认次数和可解释性。

### 评测样本

- 只读解释：理解模块、追踪调用链、审查当前 diff；
- 单文件修改：添加校验、修复小缺陷、补充单元测试；
- 多文件修改：实现接口并同步测试；
- 分支任务：测试失败后诊断和二次修复；
- 并行任务：独立读取、测试、静态检查；
- 中断任务：等待审批、命令执行中、补丁应用后中断；
- 拒绝场景：工作区外路径、敏感文件、危险命令、无沙箱命令。

## 7. 当前决策与开放项

已确定的方向：本地优先、P0 采用自研轻量状态机、持久化任务状态、结构化工具调用、策略先于执行、写入和命令的 fail-closed 恢复；ReAct 默认 10 轮，11-15 轮需有新证据或验证进展，超过 15 轮逐轮等待用户确认。

尚未确定：是否采用完整 DAG 还是更受限的阶段图；是否在 P0 支持动态追加节点；SQLite 的具体 schema 与迁移机制；并行度与资源锁粒度；沙箱后端的最低运行环境；图的可视化和调试接口。

在阶段 A-D 评测完成前，不应将“执行图”写入对外能力承诺，也不应以它为由提前实现任意命令执行或自动写入。
