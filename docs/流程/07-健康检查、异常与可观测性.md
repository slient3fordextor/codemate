# 健康检查、异常与可观测性

## 健康检查流程

`GET /health` 和 `GET /api/v1/health` 共用同一构造函数，返回：

- `status: ok`；
- 应用名称和版本；
- `config: ok`；
- `storage: enabled/disabled`，取决于 `STORAGE_ENABLED`；
- `model: configured/not_configured`。

模型健康状态的判断仅检查：provider 为 `mock`，或已设置 API Key。它不会探测外部模型地址、数据库连接或文件系统可读性，因此“ok”表示配置层可用，不表示所有依赖已连通。

`GET /api/v1/version` 返回应用名、版本和固定 API 版本 `v1`。

## 错误处理流程

```text
请求校验失败
  -> RequestValidationError
  -> 422 / VALIDATION_ERROR

业务代码显式抛出 AppError
  -> 使用异常自带 code、message、status_code

其他未捕获异常
  -> 服务端记录异常日志
  -> 500 / INTERNAL_ERROR
```

统一 HTTP 错误体结构为：

```json
{
  "error": {
    "code": "...",
    "message": "...",
    "request_id": "..."
  }
}
```

对话流中的模型故障例外：`ModelProviderError` 在生成器内被转成状态码仍为 200 的 SSE `error` 事件，其数据包含模型错误码、消息和请求 ID。浏览器应以事件而不是 HTTP 状态码判断这类失败。

## 日志与关联

每个请求都会持有 `x-request-id`。访问日志开启时，日志含 request ID、HTTP 方法、路径、状态码与延迟；未捕获异常日志额外记录方法和路径。当前日志使用标准文本格式，`LOG_JSON_ENABLED` 配置尚未被 `configure_logging()` 使用。
