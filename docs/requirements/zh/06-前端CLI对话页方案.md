# 前端 CLI 对话页方案

## 1. 背景

CodeMate MVP 阶段需要提供基础 Web 工作台，用于支持本地项目中的对话式编程、代码解释、错误分析和小范围修改。

当前后端已经具备基础对话能力：

- `POST /api/v1/chat/completions`
- SSE 流式输出事件：`message.start`、`message.delta`、`message.done`、`error`
- 请求字段支持 `session_id`、`message`、`messages`、`current_file`、`selected_text`
- L1 会话记忆可按 `session_id` 保留最近多轮上下文

但项目文件树、文件读取、命令执行沙箱和任务状态能力还处于设计或后续实现阶段。因此第一版前端应优先复用现有对话接口，聚焦“CLI 命令行开发”的高频场景。

## 2. 设计目标

CLI 对话页用于帮助开发者完成以下工作：

- 生成开发、测试、启动、构建、调试命令。
- 解释 CLI 命令的含义和风险。
- 分析终端报错、测试失败、依赖安装失败和服务启动失败。
- 根据当前文件或选中文本补充上下文进行追问。
- 以流式输出方式降低等待感。

## 3. 方案对比

### 3.1 方案一：右侧 AI 对话面板 + 底部终端

布局示意：

```text
左侧：项目文件树
中间：代码/文件预览
右侧：AI 对话
底部：CLI 命令输出区
```

特点：

- AI 负责解释命令、生成命令和分析报错。
- 用户可以从 AI 回复中复制命令到终端。
- 底部终端展示 `pytest`、`uvicorn`、`npm run dev`、`git status` 等结果。
- 后续可扩展“运行测试”“查看日志”“应用修改”等能力。

优点：

- 接近 IDE 工作台体验。
- 长期扩展性最好。
- 适合承载文件树、代码预览、任务状态和终端输出。

缺点：

- 第一版开发量较大。
- 对项目文件接口、命令执行沙箱和任务状态能力有更强依赖。

### 3.2 方案二：类 ChatGPT 页面 + 命令卡片

布局示意：

```text
顶部：项目名 / 当前模型 / 会话状态
中间：消息流
底部：输入框
消息内：命令卡片、代码块、报错分析
```

AI 生成命令时，不只展示普通代码块，而是渲染为命令卡片：

```text
pytest tests/test_chat.py -q

[复制] [解释] [标记为已执行]
```

当用户粘贴终端报错时，AI 回复按以下结构组织：

- 错误原因
- 可能相关文件
- 修复建议
- 下一条建议命令

优点：

- 实现最快。
- 与现有 SSE 对话接口最匹配。
- 不依赖完整文件树、命令执行沙箱和任务系统。
- 可以先验证 CLI 开发场景是否成立。

缺点：

- 项目文件树、代码查看和终端状态展示较弱。
- 当任务复杂度提高时，单一消息流会逐渐拥挤。

### 3.3 方案三：任务流页面

布局示意：

```text
左侧：任务列表
中间：当前任务步骤
右侧：AI 协作区
底部：命令历史 / 日志
```

每次 CLI 开发被建模为一个任务：

```text
任务：修复测试失败

1. 分析 pytest 报错
2. 定位相关文件
3. 生成修改建议
4. 运行验证命令
5. 总结结果
```

优点：

- 适合复杂开发任务。
- 体验更接近 Agent 工作流。
- 便于沉淀任务状态、命令历史和最终结果。

缺点：

- 对后端任务状态、命令执行沙箱和文件修改能力依赖较强。
- 不适合作为当前 MVP 的第一版前端。

## 4. 推荐方案

MVP 第一版推荐采用：

```text
方案二：类 ChatGPT 页面 + 命令卡片
```

推荐理由：

- 可以直接接入现有 `/api/v1/chat/completions` 接口。
- 可以完整验证 SSE 流式输出体验。
- 能覆盖 CLI 开发中的高频任务：生成命令、解释命令、分析报错、给出下一步。
- 不会被尚未实现的文件树、命令执行沙箱和任务状态系统阻塞。
- 后续可以平滑演进为方案一的完整 Web 工作台。

## 6. 第一版功能范围

### 6.1 P0 功能

| 功能 | 说明 |
| --- | --- |
| 流式对话 | 接入 SSE，逐步展示 AI 输出 |
| 多轮会话 | 使用 `session_id` 保持最近上下文 |
| 多行输入 | 支持描述任务、粘贴报错、粘贴日志 |
| 命令卡片 | 自动识别回复中的 shell 命令并增强展示 |
| 复制命令 | 命令卡片提供复制操作 |
| 解释命令 | 命令卡片可触发追问，让 AI 解释命令作用 |
| 错误展示 | SSE `error` 事件展示清晰错误原因 |
| 当前文件上下文 | 输入时可携带 `current_file` |
| 选中文本上下文 | 输入时可携带 `selected_text` |

### 6.2 P1 功能

| 功能 | 说明 |
| --- | --- |
| 命令风险提示 | 对删除、覆盖、安装、网络请求等命令做提醒 |
| 标记已执行 | 用户可标记命令是否已经执行 |
| 报错模板化分析 | 粘贴报错后按固定结构组织回复 |
| 会话侧栏 | 展示最近会话列表 |
| 模型选择 | 允许切换后端可用模型 |

### 6.3 暂不进入第一版

| 功能 | 原因 |
| --- | --- |
| 内置终端执行命令 | 需要命令执行沙箱和权限治理 |
| 自动修改文件 | 需要变更预览、应用修改和回滚能力 |
| 完整项目文件树 | 需要文件访问接口和安全边界先落地 |
| 任务编排视图 | 依赖任务状态系统 |

## 7. 交互原则

- AI 回复 CLI 命令时，应优先给出可复制命令，再解释命令用途。
- 对高风险命令，应提示风险和建议确认点。
- 对报错分析，应先指出最可能原因，再给最小验证命令。
- 不在第一版中自动执行命令，避免安全边界不清。
- 保持输入框对长日志友好，支持多行、滚动和快捷发送。

## 8. 接口对接

请求接口：

```text
POST /api/v1/chat/completions
```

推荐请求：

```json
{
  "session_id": "ses_cli_chat",
  "message": "解释这个 pytest 报错并给出下一步命令",
  "current_file": "tests/test_chat.py",
  "selected_text": null,
  "stream": true
}
```

需要处理的 SSE 事件：

| 事件 | 前端行为 |
| --- | --- |
| `message.start` | 创建 AI 消息占位 |
| `message.delta` | 追加流式文本 |
| `message.done` | 标记消息完成，解析命令卡片 |
| `usage.update` | 可选展示 token 或成本信息 |
| `task.update` | 第一版可记录，暂不强展示 |
| `error` | 展示错误提示和重试入口 |

## 9. 演进路径

```text
第一阶段：CLI Chat
  -> 接入 SSE 对话
  -> 命令卡片
  -> 报错分析
  -> 当前文件/选中文本上下文

第二阶段：轻量工作台
  -> 左侧项目文件树
  -> 中间代码预览
  -> 右侧 AI 对话

第三阶段：完整工作台
  -> 底部命令输出区
  -> 任务状态
  -> 变更预览
  -> 应用修改

第四阶段：Agent 工作流
  -> 命令执行沙箱
  -> 多步骤任务
  -> 自动验证
  -> 结果总结
```

## 10. 结论

当前阶段最优解是先实现“类 ChatGPT 页面 + 命令卡片”的 CLI 对话页。

该方案能最快复用现有后端能力，验证用户在 CLI 开发场景中的真实需求，同时保留向完整 Web 工作台演进的空间。
