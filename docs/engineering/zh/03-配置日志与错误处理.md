# 配置、日志与错误处理

## 目标

建立后端基础设施能力，包括强类型配置、结构化日志、请求追踪和统一错误响应。

## 配置设计

建议使用 `pydantic-settings`。

配置入口集中在 `app/core/config.py`。更完整的配置管理说明见 [10-配置管理设计.md](10-配置管理设计.md)。

核心配置项：

```text
APP_NAME
ENVIRONMENT
LOG_LEVEL
WORKSPACE_ROOT
DATABASE_URL
MODEL_PROVIDER
MODEL_BASE_URL
MODEL_API_KEY
MODEL_TIMEOUT_SECONDS
MODEL_MAX_RETRIES
```

配置读取应集中在 `app/core/config.py`，业务代码通过依赖注入或 settings 对象获取配置，不直接读取环境变量。

当前脚手架将配置分为：

| 分组 | 用途 |
| --- | --- |
| `settings.app` | 应用名称、版本、环境和 debug |
| `settings.workspace` | 本地工作区根路径、文件大小限制和目录规模限制 |
| `settings.storage` | 数据库地址和持久化开关 |
| `settings.model` | 模型 provider、base url、模型名、API Key、超时和重试 |
| `settings.security` | 敏感信息检测和限流 |
| `settings.logging` | 日志级别、JSON 日志和访问日志 |

## 日志设计

日志应包含：

- `request_id`
- `task_id`
- `route`
- `status_code`
- `latency_ms`
- `model_provider`
- `model_name`
- `error_code`

日志不应包含：

- 明文 API Key。
- 完整源码。
- 完整 prompt。
- 用户私密路径的无必要细节。

## 错误响应格式

建议统一格式：

```json
{
  "error": {
    "code": "MODEL_PROVIDER_TIMEOUT",
    "message": "Model provider request timed out",
    "request_id": "req_..."
  }
}
```

常见错误码：

```text
VALIDATION_ERROR
WORKSPACE_PATH_FORBIDDEN
SENSITIVE_CONTENT_DETECTED
MODEL_PROVIDER_TIMEOUT
MODEL_PROVIDER_UNAVAILABLE
TASK_NOT_FOUND
RATE_LIMITED
INTERNAL_ERROR
```

## 中间件

建议增加：

- request id 中间件。
- 访问日志中间件。
- 异常处理器。
- CORS 中间件，按前端开发需要配置。

## 验收标准

- 所有错误响应结构一致。
- 每个请求都有 `request_id`。
- 日志不会泄露密钥和完整源码。
- 配置项有默认值、类型约束和错误提示。

## 风险点

- 没有统一错误模型会让前端、CLI 和插件分别处理不同错误格式。
- 没有日志脱敏会破坏本地优先产品的信任边界。
