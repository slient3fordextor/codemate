# 主流多语言代码助手设计对比

## 目标

梳理主流 IDE、编辑器和 AI 代码助手在多编程语言支持上的常见设计，并给出 CodeMate 可采用的路线。

本文档不是产品竞品分析，而是工程设计参考。

## 主流设计路线总览

| 路线 | 代表系统 | 核心思路 | 优势 | 代价 |
| --- | --- | --- | --- | --- |
| LSP 路线 | VS Code、Neovim、Zed | 每种语言启动 Language Server，统一走 LSP 协议 | 标准化、语言覆盖广、诊断和跳转成熟 | 进程管理复杂，对本地环境依赖强 |
| 自研语义模型路线 | JetBrains IDE | 自研 PSI/AST/索引系统，每种语言深度插件化 | 重构和静态分析能力强 | 开发成本极高，短期不适合小团队 |
| tree-sitter 路线 | GitHub、Cursor 类编辑器、部分现代编辑器 | 用增量解析器获取语法树和符号片段 | 轻量、速度快、适合代码切块 | 语义能力弱于 LSP |
| 文本检索路线 | 早期 AI 代码助手、轻量 Web IDE | 文件树、关键词、路径和简单规则检索 | 实现快、部署简单 | 对跨文件理解有限 |
| 索引服务路线 | Sourcegraph 类系统 | 建立项目级或仓库级代码索引 | 适合大型仓库和团队场景 | 存储、同步、权限和成本更复杂 |
| Agent 工具路线 | Claude Code、Codex CLI 类工具 | 让模型调用文件、搜索、测试、补丁等工具 | 修改闭环强，适合任务自动化 | 权限、安全和可控性要求高 |

## 路线一：LSP

LSP 的核心思想是把编辑器和语言能力分离：

```text
Editor / Client
  |
  | JSON-RPC
  v
Language Server
  |
  v
Compiler / Type Checker / Analyzer
```

常见能力：

- 诊断错误。
- 定义跳转。
- 查找引用。
- 自动补全。
- hover 文档。
- 重命名。
- 代码格式化。

适合 CodeMate 的部分：

- 后续语义级能力可以接入 LSP。
- 每种语言不需要自己重写类型分析。
- 可以把 LSP 作为独立服务或可选能力，不进入 MVP 主流程。

不建议 MVP 一开始完整接 LSP：

- 需要管理多个语言服务器进程。
- 用户本地环境差异大。
- Python、TypeScript、Go、Rust 的 LSP 安装和启动方式都不同。
- Web 后端服务要处理超时、崩溃、缓存和并发。

CodeMate 建议：LSP 放在 L3 阶段，先为接口预留，不作为第一阶段依赖。

## 路线二：JetBrains 式深度语义模型

JetBrains IDE 的典型做法是围绕项目模型、语法树、符号表和索引建立完整 IDE 平台。每种语言通过插件深度接入。

优势：

- 静态分析深。
- 重构可靠。
- 对大型工程和企业开发体验好。

代价：

- 需要大量语言工程投入。
- 插件体系复杂。
- 很难在轻量 Web 后端中短期复制。

CodeMate 建议：只借鉴“项目模型”和“语言插件化”思想，不走完整自研语义平台。

## 路线三：tree-sitter

tree-sitter 是轻量级语法解析路线，适合做代码切块和符号提取。

常见用途：

- 识别函数、类、方法。
- 按语法节点切分代码。
- 做语法高亮。
- 构建轻量符号摘要。

优势：

- 比纯文本规则稳定。
- 比 LSP 轻。
- 不依赖用户完整开发环境。

局限：

- 它主要理解语法，不理解完整类型语义。
- 跨文件引用和复杂类型推导仍然有限。

CodeMate 建议：tree-sitter 是 L2 到 L3 的过渡方案。可以优先用于“相关代码片段切分”和“文件摘要生成”，再决定是否接 LSP。

## 路线四：文本检索和规则检索

这是 AI 代码助手最容易落地的路线。

常见信号：

- 当前文件。
- 选中代码。
- 用户输入中的文件名、函数名、类名。
- 同目录文件。
- 测试文件命名规则。
- 项目配置文件。

优势：

- 实现成本低。
- 与 FastAPI 后端和本地文件安全边界容易集成。
- 对 MVP 足够实用。

局限：

- 不知道真正的调用关系。
- 对大型仓库召回不稳定。

CodeMate 建议：MVP 采用这条路线作为基础能力，同时把 adapter 抽象设计好，避免后面接 tree-sitter / LSP 时推倒重来。

## 路线五：代码索引服务

大型代码助手通常会建立项目级索引。

索引内容可能包括：

- 文件树。
- 文件摘要。
- 符号列表。
- 依赖关系。
- embedding 向量。
- 最近修改记录。

优势：

- 对大型项目更稳定。
- 可以跨会话复用。
- 便于做“问整个项目”的能力。

代价：

- 需要持久化。
- 需要处理索引更新。
- 需要权限隔离。
- embedding 成本和隐私风险更高。

CodeMate 建议：短期只做轻量文件树和规则检索。后续如果进入团队版或大型仓库场景，再引入 SQLite 索引表和可选向量索引。

## 路线六：Agent 工具调用

现代代码 Agent 常见做法是让模型使用工具：

```text
模型
  -> search files
  -> read file
  -> edit file
  -> run tests
  -> inspect errors
  -> revise patch
```

优势：

- 可以完成真实修改闭环。
- 不要求一次性把所有上下文塞进 prompt。
- 能通过测试反馈迭代。

风险：

- 文件写入和命令执行需要权限控制。
- 错误操作会影响用户项目。
- 长任务需要状态管理、取消、日志和恢复。

CodeMate 建议：Agent 工具调用属于 L4 能力。当前应先把只读上下文、语言 adapter、任务状态和权限边界打牢。

## 主流系统的共性

无论具体路线不同，成熟系统通常都有这些共同点：

1. **语言插件化**：语言差异被限制在插件、server 或 adapter 中。
2. **项目模型优先**：不仅看单文件，还看配置、依赖、测试和目录结构。
3. **上下文预算控制**：不会无限读取项目文件。
4. **渐进增强**：纯文本能力、语法能力、语义能力、自动修改能力逐步叠加。
5. **安全边界明确**：读取文件、发送模型、执行命令、写入文件是不同权限级别。
6. **可降级**：未知语言或环境缺失时仍然能按文本处理。

## CodeMate 推荐组合

CodeMate 不建议复制单一路线，而是采用组合式路线：

```text
MVP:
  文本检索 + 规则检索 + 语言 adapter

增强:
  tree-sitter 语法切块 + 轻量符号摘要

语义阶段:
  可选 LSP 集成

Agent 阶段:
  文件编辑 + 测试执行 + patch 校验 + 任务系统
```

推荐架构：

```text
ChatService
  |
  v
PromptBuilder
  |
  v
LanguageContextService
  |
  +-- LanguageDetector
  +-- LanguageRegistry
  +-- PythonAdapter
  +-- TypeScriptAdapter
  +-- GoAdapter
  |
  v
WorkspaceFileAdapter
```

后续增强时：

```text
LanguageContextService
  |
  +-- RuleBasedCollector
  +-- TreeSitterSymbolExtractor
  +-- OptionalLspClient
  +-- ProjectIndexStore
```

这样既能快速支持多语言，又不会把 ChatService 变成复杂的语言分支集合。

## 与 CodeMate 当前架构的关系

当前已有模块：

| 已有能力 | 可复用方式 |
| --- | --- |
| `ChatService` | 接入语言上下文生成，不直接处理语言细节 |
| `ModelAdapter` | 继续只负责模型调用，不关心语言 |
| `settings.workspace` | 作为文件访问和上下文收集的安全根 |
| L1 会话记忆 | 保持只保存最近对话，不保存当前文件和选中文本 |
| SSE 对话接口 | 可以流式返回带语言上下文的模型输出 |

需要新增模块：

| 新模块 | 目的 |
| --- | --- |
| `LanguageDetector` | 识别当前语言和项目类型 |
| `LanguageAdapter` | 封装每种语言规则 |
| `LanguageContextService` | 统一收集语言相关上下文 |
| `PromptBuilder` | 统一把语言上下文转成模型消息 |

## 取舍结论

CodeMate 的主路线应是：

1. **短期采用 adapter + 规则检索**，快速支持 Python、JavaScript、TypeScript。
2. **中期引入 tree-sitter**，提升代码片段切分和符号摘要质量。
3. **长期可选接入 LSP**，提供定义、引用、诊断等语义能力。
4. **Agent 阶段再做命令执行和自动修改闭环**，并纳入任务系统和权限控制。

这条路线实现成本可控，也与当前 FastAPI、模型适配器、本地工作区安全边界和 L1 记忆设计兼容。
