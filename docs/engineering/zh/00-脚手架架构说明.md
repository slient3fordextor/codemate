# 脚手架架构说明

## 目标

本文聚焦 CodeMate FastAPI 脚手架本身，说明每个目录、分层和基础设施分别是为了做什么。

脚手架不是业务功能集合，而是后续开发的约束框架。它的价值是让对话、项目文件、模型适配、任务状态、存储和测试各自有明确位置，避免所有逻辑堆到 API 层或入口文件里。

## 总体分层

```text
app/main.py
  |
  v
app/api
  |
  v
app/services
  |
  +--> app/adapters
  |
  +--> app/storage
  |
  v
app/schemas

app/core 为所有层提供配置、日志、错误和中间件。
tests 验证脚手架和业务行为。
```

## 架构分层用途

| 架构 | 位置 | 用途 |
| --- | --- | --- |
| 应用入口 | `app/main.py` | 创建 FastAPI 应用，注册路由、中间件、异常处理和生命周期 |
| API 层 | `app/api` | 暴露 HTTP 接口，只处理请求解析、响应返回和依赖注入 |
| Schema 层 | `app/schemas` | 定义 API 请求和响应结构，保证 OpenAPI 与前后端契约稳定 |
| Service 层 | `app/services` | 承载业务编排，例如对话流程、上下文构建、任务流转 |
| Adapter 层 | `app/adapters` | 对接外部系统，例如模型 API、本地文件系统、第三方服务 |
| Storage 层 | `app/storage` | 封装数据库、会话、任务、反馈和项目索引持久化 |
| Core 层 | `app/core` | 提供配置、日志、统一错误、中间件等基础设施 |
| Tests | `tests` | 固化脚手架契约，防止后续重构破坏启动、接口和安全边界 |

## 每个目录是为了做什么

### `app/main.py`

用于创建应用实例。

它应该做：

- 创建 `FastAPI`。
- 注册 `/api/v1` 路由。
- 注册 request id、访问日志等中间件。
- 注册统一异常处理器。
- 注册启动和关闭生命周期。

它不应该做：

- 不直接调用模型。
- 不直接读写本地文件。
- 不直接访问数据库。
- 不写对话、任务、项目索引等业务逻辑。

### `app/api`

用于组织 HTTP 接口。

它解决的问题是：把外部请求转换成内部服务调用，并把内部结果转换成 HTTP 响应。

典型模块：

```text
app/api/v1/health.py
app/api/v1/chat.py
app/api/v1/projects.py
app/api/v1/models.py
app/api/v1/tasks.py
```

API 层应该保持薄，不承载复杂业务。比如 `chat.py` 可以接收请求并调用 `ChatService`，但不应自己拼 prompt、检索文件或调用模型 SDK。

### `app/api/v1/router.py`

用于汇总 v1 版本的全部路由。

它的作用是让版本化 API 有一个统一入口，后续新增 `v2` 时可以并行存在，降低 Web、CLI、IDE 插件的升级风险。

### `app/schemas`

用于定义请求和响应结构。

它解决的问题是：让 API 契约稳定、可校验、可生成 OpenAPI。

示例：

- `HealthResponse`
- `ErrorResponse`
- `ChatRequest`
- `ChatChunk`
- `TaskResponse`
- `ProjectTreeResponse`

Schema 不等于数据库模型。API 返回给前端的字段和数据库内部存储字段应该可以独立演进。

### `app/services`

用于承载业务编排。

它解决的问题是：把多个底层能力组合成一个用户可见的流程。

典型服务：

```text
ChatService
ContextService
TaskService
ProjectService
ModelConfigService
```

例如一次对话请求中，service 层可以负责：

1. 创建任务。
2. 读取当前文件上下文。
3. 检索相关片段。
4. 调用模型适配器。
5. 流式返回结果。
6. 更新任务状态和 usage。

### `app/adapters`

用于隔离外部系统和不稳定依赖。

它解决的问题是：业务代码不直接依赖具体 SDK、文件系统细节或第三方服务格式。

典型适配器：

```text
app/adapters/models/openai_compatible.py
app/adapters/models/mock.py
app/adapters/filesystem.py
```

适配器应该把外部异常转换成内部统一错误。例如 OpenAI SDK 的超时异常不应直接冒泡到 API 层，而应转换为 `MODEL_PROVIDER_TIMEOUT`。

### `app/storage`

用于封装持久化。

它解决的问题是：业务层不关心数据到底来自 SQLite、PostgreSQL 还是内存 mock。

典型内容：

- 数据库连接。
- ORM 模型。
- Repository。
- 迁移脚本入口。

MVP 可以先不用复杂数据库，但仍建议保留 storage 边界，为会话、消息、任务、反馈和项目索引做准备。

### `app/core`

用于放全局基础设施。

它解决的问题是：所有横切能力统一实现，不散落在业务代码里。

当前脚手架包含：

- `config.py`：强类型配置。
- `logging.py`：日志初始化。
- `errors.py`：统一异常和错误响应。
- `middleware.py`：request id 和访问日志。

后续可继续加入：

- CORS 配置。
- 限流。
- 鉴权。
- 敏感信息脱敏。
- 生命周期资源管理。

### `tests`

用于验证脚手架契约。

它解决的问题是：后续新增业务时，不能破坏基础启动、API 前缀、健康检查、错误格式和安全边界。

第一阶段至少测试：

- 应用可以创建。
- `/api/v1/health` 可访问。
- `/api/v1/version` 可访问。
- 响应包含 `x-request-id`。

后续增加项目文件访问后，应优先补路径穿越和敏感文件测试。

## 当前脚手架对应关系

| 已落地内容 | 解决的问题 |
| --- | --- |
| `main.py` | 兼容根目录导入，导出 `app.main:app` |
| `app/main.py` | FastAPI 应用工厂和应用组装 |
| `app/api/v1/health.py` | 基础健康检查和版本信息 |
| `app/api/v1/router.py` | v1 路由统一入口 |
| `app/core/config.py` | 强类型配置和环境变量读取 |
| `app/core/errors.py` | 统一错误响应模型 |
| `app/core/middleware.py` | request id 和访问日志 |
| `app/schemas/health.py` | 健康检查响应契约 |
| `app/schemas/errors.py` | 错误响应契约 |
| `tests/test_health.py` | 验证基础 API 和 request id |
| `pyproject.toml` | 统一依赖、测试、lint、类型检查配置 |
| `Makefile` | 固定开发命令 |

## 为什么先做这些

CodeMate 后续核心复杂度在模型调用、上下文检索、本地文件安全、SSE 流式输出和任务状态。如果没有脚手架约束，这些能力很容易互相耦合。

先搭建当前脚手架，是为了提前固定几条边界：

- API 层不直接做业务。
- Service 层负责编排。
- Adapter 层隔离外部系统。
- Storage 层隔离持久化。
- Core 层统一横切能力。
- Schema 层稳定接口契约。
- Tests 保证这些契约不被破坏。

## 后续扩展位置

| 要新增的能力 | 应放位置 |
| --- | --- |
| 对话 HTTP 接口 | `app/api/v1/chat.py` |
| SSE chunk schema | `app/schemas/chat.py` |
| 对话编排 | `app/services/chat.py` |
| 上下文裁剪 | `app/services/context.py` |
| 本地文件读取 | `app/adapters/filesystem.py` |
| OpenAI 兼容模型 | `app/adapters/models/openai_compatible.py` |
| Mock 模型 | `app/adapters/models/mock.py` |
| 任务状态 API | `app/api/v1/tasks.py` |
| 任务服务 | `app/services/tasks.py` |
| 任务存储 | `app/storage/tasks.py` |
| 路径安全测试 | `tests/test_filesystem_security.py` |
| SSE 测试 | `tests/test_chat_stream.py` |

## 脚手架验收标准

- 新开发者能从目录名判断代码应该放哪里。
- API、业务、外部系统、存储和基础设施没有混在一起。
- 应用可以通过 `uvicorn app.main:app --reload` 启动。
- `/api/v1/health` 和 `/api/v1/version` 可访问。
- `pytest`、`ruff`、`mypy` 可以作为基础质量门禁。
