# L1 会话记忆设计

## 相关文档

- `docs/requirements/zh/01-产品需求.md`：P0 要求支持多轮对话，单个会话至少保留最近 10 轮上下文。
- `docs/engineering/zh/06-SSE流式对话接口.md`：定义 `POST /api/v1/chat/completions`，请求已包含 `session_id`。
- `docs/engineering/zh/08-任务状态与存储设计.md`：定义后续持久化边界，建议会话元数据和消息摘要可持久化，但不持久化大段 prompt 原文。

## 目标

L1 会话记忆用于满足 MVP 的多轮对话能力：同一个 `session_id` 下，服务端自动把最近若干轮用户问题和助手回答带入下一次模型请求。

L1 不解决跨进程、重启后恢复、跨项目长期偏好学习，这些属于 L2/L3 能力。

## 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 客户端传完整 `messages` | 前端每次把历史消息全部传给后端 | 后端最简单，无服务端状态 | 每个客户端都要实现裁剪；历史可能被重复上传；难以统一安全策略 |
| 进程内 LRU 会话记忆 | 后端按 `session_id` 在内存保存最近 N 轮 | 实现快；无新依赖；适合本地 MVP；隐私风险比落盘低 | 服务重启丢失；多进程不共享 |
| SQLite 持久化消息 | 使用数据库保存会话和消息摘要 | 可恢复、可删除、可查询 | 需要迁移、数据模型和清理策略；MVP 改动更大 |
| 向量库/摘要记忆 | 对历史做摘要或向量检索后注入 | 适合长上下文和长期项目记忆 | 复杂度高；需要检索质量评估，不适合当前第一步 |

## 推荐方案

MVP 先选择“进程内 LRU 会话记忆”。

原因：

- 当前项目已有 `session_id` 字段，但存储层还未实现，进程内方案能最小改动补齐 P0 多轮对话。
- L1 只保留最近 10 轮用户/助手消息，不保存 `current_file` 和 `selected_text`，降低把源码长期留在服务端内存的风险。
- 代码层通过 `SessionMemoryStore` 协议隔离存储实现，后续迁移到 SQLite 时可以保持 chat 服务接入方式不变。

## 模块设计

L1 会话记忆拆为三个核心对象：

- `SessionMemoryStore`：存储协议，定义读取历史、追加一轮对话和清空记忆的能力。
- `SessionMemoryPolicy`：记忆策略，负责校验 `max_turns` 和 `max_sessions`，并计算最大消息数。
- `InMemorySessionMemoryStore`：进程内 LRU 实现，按会话 ID 保存最近消息，并在会话数超过上限时淘汰最久未使用会话。

`ChatService` 只依赖 `SessionMemoryStore` 协议，不直接绑定内存实现。

## 行为规则

- 请求未提供 `session_id` 时，服务端生成一个新的会话 ID，并在 `message.start` SSE 事件中返回。
- 使用 `message` 字段发起的请求会读取同一 `session_id` 的历史记忆。
- 使用 `messages` 字段发起的请求视为客户端显式提供完整上下文，服务端不额外叠加历史，避免重复注入。
- `current_file` 和 `selected_text` 只注入本轮模型请求，不写入 L1 记忆。
- 每个会话最多保留最近 10 轮，也就是 20 条 `user/assistant` 消息。

## 后续演进

- L2：SQLite 持久化会话元数据和消息摘要，支持删除会话。
- L3：对长会话做摘要压缩，或引入项目级检索记忆。
- 安全治理：接入敏感信息检测后，再决定哪些消息允许进入持久化层。

## QA

### Q1：为什么每个会话最多只保留最近 10 轮？

这里的“一轮”指一条用户消息加一条助手回答，所以 10 轮最多是 20 条 `user/assistant` 消息。

10 轮是 MVP 阶段的保守默认值，主要在以下几个因素之间做平衡：

- 多轮体验：2 到 3 轮通常不够支撑连续追问，10 轮基本能覆盖一次小型编码任务的上下文。
- 成本和延迟：每次模型调用都要重新发送历史消息，保留越多轮，输入 token 越多，响应越慢，成本也越高。
- 安全边界：编程对话里可能包含代码、日志、路径和误贴的密钥。L1 虽然不落盘，但仍然是服务端状态，应该限制保留范围。
- 上下文噪声：历史不是越多越好。早期假设可能已经被后续对话推翻，过长历史会干扰模型判断当前目标。
- 内存上界：L1 是进程内存储，需要限制单个会话大小，避免长时间运行后内存持续增长。

### Q2：为什么不用“保留全部历史”？

保留全部历史会让实现看起来简单，但有几个问题：

- prompt 会不断变长，模型调用成本和延迟不可控。
- 长历史里会混入过期要求，降低回答稳定性。
- 会扩大敏感内容在服务端内存里的保留窗口。
- 本地 MVP 虽然用户量小，也应该从一开始给内存占用设上限。

因此 L1 只保留最近窗口，后续如果需要长会话能力，应改用“最近原文 + 早期摘要”的分层方案。

### Q3：为什么不按 token 数裁剪，而是按轮数裁剪？

按 token 数裁剪更精确，也更接近模型真实成本。但当前项目还没有统一 tokenizer，也没有按不同模型统计 token 的基础设施。

MVP 先按轮数裁剪有几个好处：

- 实现简单，不引入额外依赖。
- 行为容易解释和测试。
- 和产品需求里的“至少保留最近 10 轮上下文”直接对应。

后续接入真实模型 token 统计后，可以把策略升级为：

```text
优先保留最近 N 轮
再按模型上下文窗口裁剪 token
更早历史压缩成摘要
```

### Q4：为什么 `current_file` 和 `selected_text` 不写入 L1 记忆？

这两个字段可能包含完整源码或用户选中的大段代码。如果直接写入会话记忆，会带来三个问题：

- 内存膨胀更快。
- 敏感代码在服务端状态里停留更久。
- 后续追问时可能重复注入过大的代码片段，挤占真正有用的对话上下文。

当前策略是：`current_file` 和 `selected_text` 只作为本轮临时上下文参与模型请求，不进入 L1 记忆。

### Q5：10 轮以后怎么办？

超过 10 轮时，系统会丢弃最旧的 `user/assistant` 消息，只保留最近 10 轮。

这意味着很早之前的细节可能不再被模型看到。如果需要长期保持任务目标、关键决策或项目约定，后续应增加 L2/L3 能力：

- L2 会话摘要：把早期对话压缩成短摘要。
- L2 持久化：用 SQLite 保存会话元数据和消息摘要，并支持删除。
- L3 长期记忆：保存用户偏好、项目约定和稳定事实。

成熟形态不是简单保留更多原文，而是分层记忆：

```text
L1：最近几轮原文，保证连续追问
L2：会话摘要，保留任务目标和关键决策
L3：项目/用户长期记忆，保留偏好和约定
```
